The cloud backend, and why it looks like this

A third backend beside the local Python server and the offline build: accounts, durable storage on the VPS, and several people editing one screenplay at once. This is the why document — what was chosen, what was rejected, and exactly how far the verification goes.

The problem

Faaglarna had two backends and no way to write with anyone. The local Python server kept files on disk under scripts/. The offline build ran the same frontend on GitHub Pages, with static/backend.js answering every /api/* call from IndexedDB.

Neither survived losing a browser profile, and neither let two people open the same script. The job was a third backend on the Netcup VPS that already runs api.ukeportalen.no.

Two findings that shaped everything

Both came from reading the existing code before designing anything, and both made the work far smaller than it first looked.

The fetch shim was already there

backend.js monkey-patches window.fetch. Every one of app.js's ~20 fetch('/api/...') calls goes through it, and it already had detect() and adaptUi() for switching per mode. Cloud mode became a third branch in a seam that already existed: rewrite the URL onto the API origin, attach a bearer token.

app.js's data layer needed no changes at all.

markDirty was already the universal mutation hook

Fifteen places in app.js assign to the textarea. Nine call markDirty() immediately after. Five are document load or clear, which must not reach the CRDT. One — applySmartUppercase — mutates without it.

So pushing local edits into the CRDT is one wrapper around markDirty plus one around applySmartUppercase, rather than fifteen separate rewrites.

Incidental find

applySmartUppercase not calling markDirty is a real pre-existing bug in every mode — that edit never schedules an autosave on its own. The wrapper fixes it in cloud mode. The local and offline modes still have it.

Choosing a backend

Decided once at boot, in priority order. The fetch wrapper waits for this before routing anything.

Topology

One Node process with two listeners, plus a stateless Python sidecar that never faces the internet.

The sync loop

The subtlest mechanism in the whole thing, and the one worth re-reading before changing anything in the editor.

Why diff instead of intercepting each edit

The alternative was describing each of the fifteen mutation sites as an explicit range operation. That is fragile in the worst way: one missed site silently desyncs the document with no error anywhere.

The diff trims a common prefix and a common suffix — O(n) in two scans. Every real edit (a keystroke, a Tab-cycle, a find/replace hit) is one contiguous change, so this locates it exactly. At screenplay sizes it costs far less than the re-render that follows it.

Coming back the other way, setRangeText(..., 'preserve') replaces only the changed span and lets the browser adjust the selection. A blunt ta.value = next would drop the caret to position 0 every single time a collaborator typed.

Decisions

The chips say how far each one is proven — not how confident it feels.

The Y.Doc is the source of truth

Verified

doc_state.ydoc holds the CRDT. Plain text is derived from it on demand for exports, snapshots and /api/file — never stored beside it, so there is no cache that can go stale.

Reads go through a Hocuspocus direct connection, which serves the in-memory document when one is loaded and the database when it isn't. Reading doc_state directly would return a copy up to one debounce interval old, and silently export stale PDFs.

/api/save changed meaning instead of disappearing

Verified

Autosave returns 200 and does nothing — the CRDT already persisted continuously. A manual Ctrl+S materialises the text and writes a doc_versions row.

That gives the existing history panel a natural cloud meaning — manual saves are named versions — without touching it. The 409 "changed on disk" prompt becomes unreachable, which is correct: a CRDT merges concurrent edits rather than racing over a whole file.

Undo is per-user

Verified

app.js's undo stack snapshots the whole document. Replaying one in a shared script would also wipe out whatever a collaborator typed meanwhile.

Cloud mode delegates to Yjs's UndoManager, scoped with trackedOrigins to this browser's own edits. Outside cloud mode app.js's stack is used unchanged. There is a test asserting undo removes your text and leaves theirs.

The textarea stayed — no CodeMirror rewrite

Considered, rejected

CodeMirror 6 with y-codemirror.next would give remote carets drawn inline and Fountain syntax highlighting, but costs rewriting ~125 editor call sites onto its transaction API. Since markDirty already covered nine of ten mutation paths, the textarea binding was a fraction of the work.

The cost of that choice: no remote carets inside the editor. Collaborator initials appear in the toolbar instead. If that stops being enough, CodeMirror is the upgrade path and the server needs no changes at all.

app.js is not modified

Logic tested, DOM wiring not

cloud.js wraps four globals from outside. app.js is a classic script with no use strict, so its top-level function declarations are window properties, and reassigning them affects its own internal calls too.

This is the same override idiom backend.js already uses for window.fetch and the export button, so it matches the codebase instead of introducing a pattern. The payoff: the local and offline builds run byte-identical app.js, and nothing here can break them.

Two traps in that approach

const state is a lexical global and never lands on window — it must be reached as a bare identifier. And window.status is the browser's own status-bar string, which app.js's function status() shadows; calling it through window.status is unreliable. Both are handled by a guarded notify() helper in cloud.js.

Node for the service, Python kept for typesetting

Verified

The VPS runbook is Node-shaped and Yjs is JavaScript-native, so the service is Node. But pdf_layout.py drives ReportLab and fdx.py speaks Final Draft XML — and every export entry point was already a pure function: 

pdf_layout.build_pdf(text)                  -> bytes
pdf_layout.build_sides_pdf(text, character) -> bytes
pdf_layout.build_cue_sheet_pdf(text)        -> bytes
fdx.build_fdx(text)                         -> bytes
fdx.fdx_to_fountain(xml)                    -> str

So export-service/ is ~60 lines importing those modules unchanged. No reimplementation in JavaScript, and no second copy to keep in sync. Because it is stateless it skips almost the whole add-service runbook — no DNS, no TLS, no database, no backups. It takes no file paths either, so safe_script_path and its traversal surface never ship to the server.

scrypt, not argon2

Verified

The plan said argon2. Ukeportalen already uses scrypt from Node's built-in crypto, in a scrypt$<salt>$<hash> format. Matching it gives one convention across both services and no native module to compile on the VPS — argon2 needs node-gyp. scrypt is memory-hard and an accepted password KDF, so there is no security cost to the swap.

One deliberate difference: auth.js uses the async crypto.scrypt, not scryptSync. The same process serves collaboration sockets, and a synchronous KDF would stall every connected editor for the length of a login.

Bearer token, not a cookie

Verified

The frontend was on *.github.io and the API on its own domain, so a session cookie is a third-party cookie and is blocked by default in current browsers. Ukeportalen can use cookies only because ukeportalen.no and api.ukeportalen.no share a registrable domain. Faaglarna's own domains now share one too (lektorensrud.no), so cookies would in fact work — but the bearer token is kept: it also works from the *.github.io origin, needs no credentialed CORS, and is one less thing to get wrong.

A token in localStorage plus an Authorization header sidesteps this, and means CORS needs no credentialed mode. Sessions and invites alike are stored only as SHA-256, so a database dump cannot be replayed as a live session or a usable invite.

Hocuspocus on its own port

Verified

v4 moved off the ws package onto crossws, and handleConnection() now wants a web-standard Request rather than Node's IncomingMessage — mounting it on Express means hand-wiring the crossws Node adapter to the upgrade event. The built-in Server class is documented as unchanged for Node, so that runs on :3003 in the same process and nginx routes /collab/ to it.

Two API details that cost a correction

openDirectConnection is on Hocuspocus, not Server — reach it via server.hocuspocus. And the onAuthenticate payload carries connectionConfig, not connection. Both were found by reading the shipped type definitions rather than the docs.

Smaller calls worth remembering

Verified
  • The document name on the wire is the UUID, never the path. Paths change on rename, and a rename must not sever a live session or split a document in two.
  • Delete is a soft delete. server.py snapshots content before unlinking so history outlives the file; the cloud mirrors that with deleted_at plus a partial unique index, which also lets a new document reuse the freed path.
  • The Yjs bundle is fetched on demand. It is ~120 kB and only cloud mode needs it, so index.html does not reference it and offline visitors never download it.

Data model

users        (id, email UNIQUE, name, password_hash, created_at, last_seen)
invites      (token_hash PK, email, doc_id, doc_role, invited_by,
              expires_at, used_at, used_by)
sessions     (token_hash PK, user_id, created_at, expires_at)
documents    (id, owner_id, path, created_at, updated_at, deleted_at)
doc_access   (doc_id, user_id, role)      -- owner | editor | viewer
doc_state    (doc_id PK, ydoc BYTEA, updated_at)
doc_versions (id, doc_id, name, timestamp, content, author_id, created_at)
  • documents.path deliberately preserves path addressing, so /api/tree, /api/file?path=, rename and delete keep their existing contracts. Paths are unique per owner, not globally.
  • The owner also gets a doc_access row (role owner), so every access check is a single lookup with no special-casing.
  • doc_versions.name carries server.py's snapshot naming (YYYYMMDDTHHMMSS[-N].fountain), so /api/history returns shapes identical to the local server and the history UI needed no changes.
  • Email is stored lower-cased so a plain UNIQUE suffices. citext would need CREATE EXTENSION, which the app user may not be allowed to run.
  • Shared documents appear under Shared/<owner>/, which the tree renderer already supports as nested directories. Shared is a reserved first segment.

What's verified, and what isn't

Every suite runs with no database server and no network: db.js has a _setDriver seam that swaps in PGlite, an in-process WASM PostgreSQL 18.

Checked independently of the suites: the export sidecar's output is byte-identical to calling the library directly, and FDX round-trips losslessly across all 148 core tokens of a real script. Sections and synopses do not survive, because .fdx cannot represent them — fdx.py documents this, and it predates this work.

Verified in a browser, 28 Aug 2026

Live editing between two accounts, presence, sharing by invite link, account creation from an invite, view-only enforcement, per-user undo, password change with session eviction, all four export formats, and version history.

That pass found five bugs, every one of them in the layer with no automated coverage — which is exactly where they were predicted to be: app.js loading before the fetch shim; two successive wrong nginx location forms for the collaboration socket; manual saves never reaching the server, so version history stayed empty; and a race joining the first document. The server, which is covered, produced none.

Still not verified: undo when one person inserts a word inside a sentence another wrote. Yjs tracks character origin independently so it should behave, but that interleaving has not been tried.

Deployment

Ports to claim in the runbook's registry: 3001 REST, 3002 Python sidecar, 3003 collaboration WebSocket. The full sequence is in server-node/deploy/README-deploy.md.

The one genuine trap

The generic nginx template in README-add-service.md will break WebSockets. It sets proxy_http_version 1.1 but not the Upgrade and Connection headers, and nginx's default proxy_read_timeout of 60s drops idle editing sessions.

nginx-faaglarna.conf sets both. If collaboration connects and then dies after a minute of not typing, that is why — and it will apply to any future WebSocket service on that box.

pm2 restart sends SIGTERM, which server.js handles by calling flushPendingStores() before exiting; kill_timeout is raised to 10s for it. Restarting mid-edit does not lose the last few seconds of anyone's typing.

Open items

  • Backups are local-only. /var/backups and /var/lib/postgresql are the same filesystem, so the nightly dump survives a bad migration but not a lost VM — and doc_state.ydoc is the only copy of every script. An rclone push to personal OneDrive was built and rolled back: its token is drive-wide and Microsoft's scopes cannot be confined to one folder. Object storage with a per-bucket, write-only key is the answer that actually restricts access.
  • Operations are documented but not executed — the nightly pg_dump of faaglarna, the restore test, and the UptimeRobot monitor on /api/ready all need the server to be up first.
  • The Yjs bundle is committed, not built in CI. That keeps python server.py working with no npm and leaves the Pages workflow untouched, but it must be regenerated by hand (cd collab && npm run build) whenever the pinned versions move.
